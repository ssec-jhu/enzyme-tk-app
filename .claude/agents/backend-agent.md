# Backend Agent

This agent defines the mandatory patterns and architectural invariants for backend code in the EnzymeTK project.

## Backend Architecture
- The backend task scheduling system lives in `enzyme_tk_app/app/backend/`.
- All Dash UI code programs against the `TaskScheduler` ABC — never import Celery, Redis, or backend internals in UI code.
- **The ABC is the whole contract — 11 abstract methods.** `test_abc_has_required_abstract_methods` names all 11, but asserts `expected_methods <= TaskScheduler.__abstractmethods__` — it catches a *removed* `@abstractmethod`, never an added-but-unlisted one — so add a method and extend that set in the same change (or tighten the assertion to `==`). The newest is `count_active_jobs(session_id) -> int`, which counts the session's `ACTIVE_STATUSES` (PENDING + STARTED) jobs for the submission cap in `utils/submission_limits.py`. It is deliberately **status-only** — one `get_job_status` per id in the session set (`sismember` + `hget`, plus one `hmget` when the job is STARTED, which keeps the read-time timeout repair so a dead STARTED job stops holding a slot on the next read) — rather than `list_jobs`, whose `_read_job` does `hgetall` + `json.loads(params)` on every job, including `sequence-structure-similarity`'s base64 upload in `params["structure_content"]`. Through `list_jobs` a *rejected* submit would be the most expensive request in the app. Two things to keep true: it **issues no `expire()` of its own** — never add one; its only write is `_mark_timed_out`'s shared repair, which already moves the job hash and the session set together — and it **skips a stale id** whose hash expired before the session set (`hget` → `None` → not counted), so an expiry never costs the session a slot (`test_count_active_jobs_skips_expired_job_hashes`).
- **The cap is a throttle, not an invariant.** The count and the `submit_job` are separate round trips, so each concurrent request thread can pass the check before any of them lands: the per-session ceiling is `MAX_ACTIVE_JOBS_PER_SESSION + (workers x threads x web replicas - 1)`, i.e. **+7** for the image's `gunicorn --workers 2 --threads 4` (Dockerfile `CMD`) at the one web replica both `docker-compose.yml` and `main.bicep` (`minReplicas`/`maxReplicas: 1`) ship. That `7` is a deployment fact, not a code fact — change either and re-derive it here, in `submission_limits.py`, and in `main.bicep`'s `concurrentRequests` scale trigger. `MAX_ACTIVE_JOBS_PER_SESSION` is a **constant** in `submission_limits.py`, not an env var: it is policy the app owns, and `test_the_cap_is_a_constant_not_an_environment_variable` fails if an env read is reintroduced. The fix if the overshoot ever matters is an atomic per-session Redis counter: a **third** key, so the dual-key invariant below becomes three-way, and being session-scoped the counter inherits the extend-only rule (`gt=True` on every refresh, with the same first-touch exception — `INCR` creates the key with no TTL). TTL sync is the easy half; the hard half is DECR-exactly-once on every terminal path including a SIGKILLed worker, since a DECR against an expired counter recreates it at `-1` and frees slots forever.
- Use `get_task_scheduler()` from `enzyme_tk_app.app.backend` to obtain the singleton scheduler.
- Session management uses anonymous UUID cookies (`etk_session_id`). Access the session ID via `flask.g.session_id`.
- Each tool that does computation adds `compute.py` exporting `def run(params: dict) -> dict`. The `params` dict matches the form fields from the modal. The returned dict must be JSON-serialisable. The result and log are written to disk using the shared constants from `config.py`.
- **Result + log offload:** *Every* job's result and captured log are written to the shared volume, never stored inline in Redis. `tasks._store_result` writes `config.JOB_RESULT_FILENAME` (Redis keeps only a `{"_result_ref": ...}` pointer) and `tasks._store_log` writes `config.JOB_LOG_FILENAME` (Redis keeps *no* log body — `_read_job` defaults the field to `""` and `get_job` overlays the file from disk). Tool authors just return a plain dict. There is **no size threshold** — do not reintroduce one.
- **Single source of truth for output paths:** call `config.job_output_paths(job_id)` — the one validated choke point that turns a `job_id` into filesystem paths. It returns a `JobPaths(directory, result, log)` NamedTuple (the job dir plus the `JOB_RESULT_FILENAME` / `JOB_LOG_FILENAME` files inside it) and **raises `ValueError` if the `job_id` would escape `JOB_OUTPUTS_PATH`** (`..`, absolute, or nested), so every consumer — including the destructive `shutil.rmtree` in `_delete_job_outputs`, which catches it and refuses to delete — is guarded against path traversal. Use the tuple's `.directory` / `.result` / `.log` fields; never hardcode `os.path.join(JOB_OUTPUTS_PATH, job_id)`, never re-join the filename constants yourself, and never bypass this helper — the writer (`tasks.py`) and reader (`task_scheduler_celery.py`) must not drift.
- **Don't persist redundant/placeholder fields in Redis.** If a reader already defaults a missing hash field, do not write an empty value for it (keep the hash minimal). Collapse per-branch cleanup that is identical across success/timeout/failure into the single `finally` block rather than repeating it.
- The orphan sweep (`tasks.celery_beat_sweep_orphaned_outputs`, fired by Celery `beat` every `CELERY_SWEEP_INTERVAL_SECONDS`) deletes any `JOB_OUTPUTS_PATH/<job_id>` dir whose `job:<id>` key has expired; `_delete_job_outputs` / `clear_jobs` / `admin_purge_all` remove them on explicit delete.
- Jobs are stored in Redis with a TTL (default 24h).
- **Redis TTL invariant — dual-key sync:** Every job has two Redis keys: a *hash* (`job:<job_id>`) and a membership entry in a *session set* (`session:<session_id>:jobs`). Whenever code refreshes, sets, or resets the TTL on the job hash it **must also refresh the TTL on the session set** (and vice-versa). If only one key's TTL is extended, the other can expire first — breaking ownership checks (`_owns_job`), job listing (`list_jobs`), or leaving orphan data. Audit both keys any time you add or modify a method that calls `expire`, `hset` on a status transition, or `delete` on either key.
- **Session-set TTL is extend-only:** the session set is shared across every job the session has ever submitted, so its TTL must only ever be *extended*, never shortened — use Redis's native `expire(key, ttl, gt=True)` at every touch point that refreshes it after job submission. Without `gt=True`, a short-lived job's TTL refresh can overwrite (shorten) the session set's TTL even while a sibling long-running job is still alive, causing the session set to expire early. The one documented exception is `submit_job`'s very first `expire()` on a brand-new session set, which may still be a persistent/no-TTL key — Redis treats "no TTL" as infinite for `GT` comparison, so `gt=True` there would silently no-op and the key would never get a TTL at all.
- The `docker-compose.yml` orchestrates four services — `web`, `redis`, `worker`, and a single-replica `beat` (the orphan-sweep scheduler) — with a `job-outputs` volume shared between `web` and `worker`. `beat` only schedules, so it needs no volume. `web` and `worker` also bind-mount the tool data read-only at `/app-data` (`ETK_DATA_DIR`). A second, overlay-only file — `docker-compose.check-admin.yml`, used solely by the `check-admin` skill — adds a throwaway `web-check` service that joins the **same** `redis` and the **same** `job-outputs` volume, so renaming either means editing both files. The admin variables (`ETK_ADMIN_TOKEN`, `ETK_SECRET_KEY`, `ETK_ADMIN_SESSION_TTL_SECONDS`) and the single production variable (`APP_IN_PRODUCTION_MODE`, which gates both the job cap and the submission captcha — their policy values are constants in `utils/submission_limits.py` and `utils/captcha.py`, deliberately not env vars, and the captcha's signing key is derived from `ETK_SECRET_KEY`, which production mode therefore makes mandatory) are set on `web` only; the worker serves no HTTP and never gates a submission. `main.bicep` is the same split, and hardcodes `APP_IN_PRODUCTION_MODE=true` on its web container because nothing from `.env` reaches Azure.
- **The commented-out NVIDIA device reservation under `worker.deploy` is deliberate, not dead config** — keep it. GPU-capable steps (e.g. Func-E) select their device with `torch.cuda.is_available()`, so no code change is needed, but the reservation alone is **not** the whole opt-in: the image installs CPU-only torch by default, so a GPU also needs a rebuild with `--build-arg TORCH_INDEX_URL=https://download.pytorch.org/whl/cu124` (see `Dockerfile` and `docs/deployment-guide.md` → GPU). Uncomment the reservation on a `linux/amd64` host with the NVIDIA container toolkit. Budget ~3 GB per worker replica running a Func-E job (3 replicas by default): the worker process peaks near 2 GB, and the RxnFP encoder subprocess peaks near 2 GB of its own earlier in the run, before the worker's own peak.
- Shared constants like `TERMINAL_STATUSES` and `ACTIVE_STATUSES` (PENDING + STARTED — what `count_active_jobs` counts) live in `models.py` — import from there, never duplicate.
